# 【项目名】· 代码 → 文档反向同步

## 1 适用场景

- 新增 / 重命名 / 删除模块后，文档第 3 章（逻辑视图）与第 5 章（开发视图）需要同步
- 提交前自查"文档与代码一致"（任务书该项占 5 分，抽查不一致每处 −2）
- 生成答辩「代码走查」所需的索引表

## 2 前置条件

1. 代码已按四层结构落地（`backend/src/main/java/...`）
2. 设计说明书路径已知：`01-架构设计文档/架构设计说明书.md`
3. 接口定义集中在 `docs/api/openapi.yaml`

## 3 执行步骤

1. 运行 `python scripts/scan-structure.py <代码根目录> -o structure.md` 生成当前代码结构清单
2. 把 `structure.md` 与说明书 §3.1 模块树、§5.2 目录职责表逐项比对
3. 列出差异三类：**新增模块**、**删除模块**、**改名/移位**
4. 对新增模块：补 §3.1 模块树节点、§3.7 依赖矩阵一行、§5.2 目录职责一行
5. 对接口变化：同步 `docs/api/openapi.yaml` 与 §3.5 关键接口表
6. 更新 §8.1 追溯矩阵中受影响的 FR 行
7. 把本次同步记入 `02-开发Skill/usage-log.md`

## 4 本项目强制约束（违反即为错误）

- 文档中的目录名、模块名必须与代码**逐字一致**（大小写、单复数都要对齐）
- 模块树的一级模块必须与代码的一级包/目录一一对应
- 接口表只收录对外接口；内部方法不写入
- 不允许"文档写了但代码没有"的模块（纸面架构，一票否决风险）
- 同步只改文档结构，**不得修改代码**；若代码本身违规，另开任务修复

## 5 输出物

- `structure.md`：当前代码的模块 / 分层 / 文件数清单
- 文档差异清单（新增 / 删除 / 改名）
- 更新后的 §3.1、§3.5、§3.7、§5.2、§8.1

## 6 自检清单

- [ ] `structure.md` 的模块数 = 说明书 §3.1 模块数
- [ ] 每个模块在 §5.2 都有对应目录说明
- [ ] `docs/api/openapi.yaml` 与 §3.5 接口表一一对应
- [ ] §8.1 追溯矩阵无失效行
- [ ] 本次同步已写入 usage-log

## 7 常见错误与反例

**错误 1：只更新模块树，忘了依赖矩阵**
新增模块后 §3.7 还是旧表，评审一比对就能发现文档没跟上代码。

**错误 2：直接改文档不改 openapi.yaml**
接口契约是"代码与文档一致"的硬证据，两者不同步等于自证不一致。

**错误 3：把内部私有方法写进接口表**
§3.5 只登记对外契约；内部方法属于实现细节，写进去会让接口数量虚高。
