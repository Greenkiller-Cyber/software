# ADR-004：缓存策略

- 日期：2026-11-23
- 状态：已接受
- 涉及视图：数据 / 运行

## 背景

统计页（容量趋势、肌群分布、周报）与动作库列表属于典型"读多写少"数据，若每次实时扫 `t_set_record` 汇总，随记录增长会线性变慢。同时，**授权判断**（教练能否看某学员）属于安全性关键路径，一旦缓存就会出现"学员收回授权但教练仍可看"的严重问题。

约束：

1. 单机部署，缓存不能依赖复杂集群；
2. 统计允许分钟级滞后，但授权**零容忍**；
3. 内存预算：服务器 4G，JVM 占 1G，缓存应控制在 500MB 内。

## 备选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| A：Redis 7（独立进程） | 多实例共享；支持 TTL、原子操作、后续可扩展为分布式锁；运维简单（单容器） | 多一个进程与一次网络往返（<1ms）；需处理缓存与库不一致 |
| B：Caffeine（进程内） | 零网络开销、最快 | 单实例内存、重启即失效；未来多实例会各自为政 |
| C：不做缓存，实时聚合 | 实现最简单、绝无不一致 | 随数据量线性变慢，统计页体验差；周报生成压力大 |
| D：MySQL 物化视图 | 与库同源、无额外组件 | MySQL 无原生物化视图，需定时表模拟（本项目已用聚合表，等价） |

## 决策

采用 **Redis 7 作为集中缓存**，策略为 **Cache-Aside（读时回填、写时删除）**；**授权判断不缓存**，每次实时校验数据库。

分工：

- 缓存：容量趋势、周报、动作库列表、当前计划
- 不缓存：教练授权校验、审核状态判定、任何鉴权中间件结果

## 理由

1. **Redis 与未来的部署形态兼容**：虽然本期单实例，但预留了水平扩容与分布式锁的可能（定时任务防重复执行），Caffeine 无法平滑过渡。
2. **删除而非更新缓存**：更新缓存在并发下容易出现"旧值覆盖新值"，删除 + 下次读回填更简单可靠（并发窗口内最多一次多余回源）。
3. **授权绝不缓存是刻意决策**：缓存授权能把 QPS 降下来，但代价是"收回授权后仍有可见窗口"，这与 NFR-04（越权拦截 100%）直接冲突。**安全属性优先级高于性能**（见 §1.4）。
4. **放弃的代价**：多一个进程（约 50MB）与一次网络往返；统计页仍可能出现 10 分钟滞后，已在接口文档中标注"数据可能有延迟"。

## 影响

- **数据视图**：Key 设计、TTL、失效时机写入 §4.7；穿/击/雪三问给具体方案（空值缓存、逻辑过期+互斥重建、TTL 抖动）。
- **运行视图**：Redis 故障时降级为直接查聚合表（聚合表本身轻量），**不返回 500**；需在 §6.8 给出熔断阈值。
- **开发视图**：缓存操作统一封装在 `infrastructure/cache`，禁止在 Controller 里直接 `redisTemplate`。
- **一致性**：接受"统计最多滞后 10 分钟"，但缓存删除必须与聚合写库在同一消息消费流程内完成（先写库后删缓存）。

## 验证方式

1. 统计接口 P95：命中缓存 <50ms、未命中 <300ms，视为达标；
2. 演练：手动删除 Redis 中某用户统计 key 后，页面应在下一个请求回源并重新缓存；
3. 安全回归：收回授权后立即以教练身份访问，必须 403（**这条是硬性验收项**，不允许出现缓存窗口）；
4. 若 Redis 不可用，统计接口应降级返回数据并附"估算"标记，而不是报错。
