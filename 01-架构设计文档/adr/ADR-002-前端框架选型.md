# ADR-002：前端框架选型

- 日期：2026-11-23
- 状态：已接受
- 涉及视图：开发

## 背景

前端要支撑三类角色界面（健身者、教练、管理员），核心交互是「训练中快速记录组次」（单手操作、低延迟、防误触）与「数据可视化」（容量趋势、肌群分布、周报）。

约束：

1. 单人开发，前端不是主投入方向，希望 2–3 周完成主要页面；
2. 训练场景多在手机浏览器打开，需响应式而非原生 App；
3. 图表需要可定制能力（多序列折线、堆叠柱状）。

## 备选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| A：Vue 3 + Vite + Pinia + ECharts | 上手快、单文件组件清晰；ECharts 中文文档完善、图表类型全 | 国际化生态弱于 React；团队规范需自建 |
| B：React 18 + Next.js + Recharts | 生态最大；类型与 hooks 成熟 | 本人不熟；SSR 对登录后应用属过度设计；Recharts 复杂图表弱于 ECharts |
| C：uni-app / 小程序 | 一次开发多端 | 组件与调试受限；复杂表格图表支持差；本项目无小程序需求 |
| D：原生 HTML + jQuery | 无构建、起步快 | 状态管理会失控；不满足工程化与规范要求 |

## 决策

采用 **Vue 3 + Vite + Pinia + Vue Router + ECharts**，UI 用 Element Plus，Axios 统一封装请求与错误处理，全量 TypeScript。

## 理由

1. **投入产出比最高**：单文件组件心智负担低，7 个模块 2–3 周可完成；ECharts 直接满足 C4 可视化，无需自研图表。
2. **移动优先即可满足**：响应式布局 + 记录页大按钮（≥48px 触控区），不做原生 App，规避上架与分发成本。
3. **放弃的代价**：SSR 对登录后应用无 SEO 收益；uni-app 的多端优势在本项目用不上，反而牺牲表格与图表能力。
4. **自身代价**：类型安全弱于 React 生态，因此强制 TypeScript + ESLint/Prettier 兜底。

## 影响

- **开发视图**：前端按 `views / components / api / stores / utils` 划分，`api/` 与后端 OpenAPI 一一对应（§5.2）。
- **运行视图**：构建产物为静态文件，Nginx 托管，与后端分离部署。
- **契约**：所有请求经 `request.ts` 拦截器统一处理 `Result<T>` 与 403/409，避免各页面重复判断。
- **风险**：ECharts 体积约 300KB（gzip），需按需引入（`echarts/core` + 按图表注册）。

## 验证方式

1. 若 4G 下首屏 >3s，启用路由懒加载与 ECharts 按需引入；
2. 若低端机记录页输入延迟明显，把该页拆为独立轻量路由（不加载图表库）；
3. 第 11 周若前端进度落后超 1 周，砍掉"成就徽章"等低优先级页面，**不换框架**。
