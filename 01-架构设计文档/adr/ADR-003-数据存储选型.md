# ADR-003：数据存储选型

- 日期：2026-11-23
- 状态：已接受
- 涉及视图：数据

## 背景

系统核心数据有三类：一是强关系型业务数据（用户、计划、训练日、组次记录、审核工单），需要事务与多表关联；二是预聚合统计（日容量、周报），需要按口径稳定重算；三是文件（训练照片、动作示范）。数据量估算：DAU 2000、单用户年 400 组记录，`t_set_record` 三年约 240 万行 —— 属于**小规模**。

约束：

1. 课程明确要求"数据库必须真实使用，内存 List/Map 模拟视为未完成"；
2. 打卡与会话状态需要事务一致性（一次提交要么都成功，要么都不写）；
3. 统计需要能写 SQL 校核口径（否则无法向老师解释数字怎么来的）。

## 备选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| A：MySQL 8.0（InnoDB） | 事务与唯一约束成熟（幂等直接靠 UNIQUE 实现）；组合主键 upsert 适合聚合表；部署简单、生态普及 | 复杂分析型查询弱；JSON 函数能力弱于 PG |
| B：PostgreSQL 16 | JSONB、窗口函数、CTE 更强，适合统计；类型系统严谨 | 本机与校园服务器环境预装少，运维经验少；团队无使用经验 |
| C：MongoDB 7 | 文档模型适合"计划快照"这类嵌套结构；水平扩展方便 | 弱事务（虽支持多文档事务但成本高）；关系查询（教练-学员授权）别扭；统计要写聚合管道，校核困难 |
| D：MySQL + InfluxDB（时序库存统计） | 时序查询快 | 两套存储要保证一致性，运维与学习成本翻倍，240 万行规模用不上 |

## 决策

主存储采用 **MySQL 8.0（InnoDB，utf8mb4）**；聚合统计用**同库聚合表**（`t_daily_stat`、`t_weekly_report`），不引入第二套存储；文件走对象存储/MinIO，不入库。

## 理由

1. **事务与唯一约束是刚需**：组次记录与会话状态、审核工单与对象状态都需要本地事务；幂等设计直接依赖 `UNIQUE(client_token)` 与组合主键 upsert，这是 MySQL 的强项。
2. **口径可校核**：统计全部用 SQL 表达，老师问"肌群占比怎么算的"，可以直接把 SQL 贴出来；MongoDB 的聚合管道可读性差。
3. **规模不需要分布式**：240 万行在单机 MySQL 上是小表，引入 InfluxDB 或分库分表属于过度设计（见 §4.4 的触发条件）。
4. **放弃的代价**：PostgreSQL 的分析能力更强，但换来的是环境与经验成本；因此把"复杂统计"限制在固定几个聚合口径上，用预计算规避 SQL 短板。

## 影响

- **数据视图**：17 张表，12 张核心表给出完整数据字典（§4.2）；ER 图与建表脚本必须一致（−4 分项）。
- **开发视图**：迁移用 Flyway，脚本命名 `V{版本}__{描述}.sql`，全部入库；禁止手改生产库。
- **运行视图**：连接池 HikariCP（最大 10）；慢查询阈值 500ms，开启 `slow_query_log`。
- **物理视图**：单机部署，每日全量备份 + binlog，RPO 24h、RTO 2h。
- **风险**：MySQL 8 不支持"部分唯一索引"，`t_plan` 的"单用户仅一个进行中计划"需用应用层约束或生成列实现（已在 §4.2 标注）。

## 验证方式

1. 若 `t_set_record` 上"按用户+时间范围"查询超过 200ms，则补组合索引 `(member_id, created_at)`；
2. 若某统计 SQL 超过 1s，改为读取聚合表（预计算），**不换数据库**；
3. 仅当单表超过 2000 万行或写入 TPS 超过 500 时，才评估分库分表或专用分析库。
